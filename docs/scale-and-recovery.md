# 规模与恢复：实测边界、瓶颈与备份/恢复怎么用

> 公开材料。本文只引用**隔离夹具**上的实测数字，不含任何私人路径、真实项目名或真实证据。
> 设计依据：DESIGN.md §2.8（分层上下文与可信覆盖）、§4.3–§4.4（防爆炸与增量刷新）、
> §8.5（连续性、归档与恢复）、§11.8（端到端验收与规模证据）。
> 复跑：`pnpm verify:v06-14`（`node --import tsx scripts/verify-v06-14.ts`）。

## 0. 一句话结论

1 千与 1 万文件档在本机**跑通且全量覆盖**；**10 万文件档跑通了流程但没有通过"全量覆盖"**——
模块图只覆盖到预算上限的 2 万文件（25%），项目扫描在 2 万条目处截断。
**本文列出的档位是测试档位，不是当前支持承诺**；未通过的地方连瓶颈与扩容触发条件一起列在 §4。

## 1. 测试档位怎么定的

- 文本文件档位：**约 1 千 / 1 万 / 10 万**，语言与目录构成固定（TypeScript 60% / Python 20% / Markdown 10% / JSON 10%，
  文件分布在 `src/modNNN/` 下，每目录约 50–350 个）。
- **任务量、事件量、关系量各自单独放大**，不靠文件数代表业务复杂度：任务 500 / 2000 张卡；
  事件 2000 / 20000 条；关系 3000 个叶子模块。
- 场景：变更风暴、超长日志、局部服务故障；前台局部读取、后台可取消、超限显示省略量。
- 夹具全部建在 `os.tmpdir()` 下的临时目录，跑完整棵删除（本卡最后一次全量复跑：
  清理前 **45.1 MB / 120325 文件 / 621 目录**，清理后已整棵删除；整轮墙钟 168 s）。

## 3. 分档实测结果

所有时间单位 ms；`索引` = 零模型 tree-sitter 静态模块图（`parseDirectory`，遍历预算 20000 文件 / 3000 ms），
`扫描` = 项目结构扫描（`scanDirectoryAsync`，预算 20000 条目 / 1500 ms），
`上下文包` = §2.8 的分层上下文包（零模型，上限 24000 字符）。

| 档位 | 文件 / 目录 / 磁盘 | 夹具生成 | 索引冷启动 | 索引增量（改 3 文件） | 索引覆盖 | 模块 / 聚合边 | 扫描 | 上下文包 | 模型输入 | RSS 前→后 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 千 | 1001 / 23 / 0.1 MB | 411 | 270（解析 252） | 222 | **100%** | 15 / 12 | 21 | 5.6 | 2141 字符 | 67 → 94 MB | **pass** |
| 1 万 | 10001 / 203 / 1.2 MB | 4082 | 2292（解析 2173） | 2177 | **100%** | 15 / 12 | 67 | 2.5 | 2157 字符 | 108 → 261 MB | **pass** |
| 10 万 | 100001 / 303 / 12.8 MB | 42927 | 3009（解析 2850，**撞 3000 ms 预算**） | 3007 | **25%**（19999/80000 源码文件） | 15 / 0 | 96（**truncated**） | 2.7 | 2173 字符 | 401 → 611 MB | **partial** |

页面交互 p50 / p95（真起后端进程 + 真 HTTP，每端点采样 7 次；四个只读端点都是 200）：

| 档位 | `GET …/scan` | `GET …/status-projection` | `GET …/plan` | `GET …/progress` |
| --- | --- | --- | --- | --- |
| 1 千 | 30.8 / 64.5 | 6.5 / 14.9 | 4.0 / 6.8 | 3.2 / 4.9 |
| 1 万 | 72.0 / 74.1 | 7.4 / 9.8 | 4.6 / 5.9 | 3.1 / 4.7 |
| 10 万 | 103.2 / 109.0 | 5.8 / 6.7 | 3.9 / 5.8 | 3.0 / 4.6 |

读法（如实）：

- **索引冷启动随文件数近似线性增长，但被预算夹住**：1 万档 2292 ms，10 万档到 3000 ms 就停手，
  所以耗时不再涨、**覆盖率掉到 25%**（`budget_exhausted=true`）。这是硬上限换来的"不卡死"，不是"能扫完"。
- **10 万档夹具本身要 43 s 才能造出来**（10 万个小文件写盘），这本身就是该档的现实成本。
- **扫描入口的响应时间反而平**（21 → 67 → 96 ms）：同样是预算先到即停，超出的部分不进结果。
- **上下文包与文件数几乎无关**（2.5–5.6 ms）：包长由图纸、相关任务与分页预算决定，不由全仓文件数决定。
- **内存随档位上涨**（1 万档峰值 261 MB，10 万档峰值 611 MB）；进程没有因为大档而崩。
- 10 万档 `聚合边 0` 是因为**模块图只覆盖前 2 万个文件**（那些文件都落在同一批模块里），不是没有依赖关系；
  该档仍解析出 6992 条 import。

## 4. 通过档位、未通过瓶颈与扩容触发条件

**通过档位**：1 千、1 万（索引与扫描均在预算内覆盖全部文件，未截断）。

**未通过档位**：10 万（`partial`）。

| 瓶颈 | 实测 | 预算（定版口径） | 后果 |
| --- | --- | --- | --- |
| 索引冷启动（tree-sitter 模块图） | 覆盖 25%（19999/80000 源码文件），耗时 3009 ms，`budget_exhausted=true` | 遍历 20000 文件 / 3000 ms | 模块图只表达前 2 万个文件，其余源码**不进图** |
| 项目扫描（结构摘要） | `truncated=true`，原因"总条目 20184 超上限 20000"，耗时 96 ms | 20000 条目 / 1500 ms | 文件树只统计到截断点（响应带 `truncated` + 原因，不冒充全量） |
| 监听预扫描（后台） | 10 万档转「仅顶层」，原因"单目录条目 10000 ≥ 上限 3000"，`truncated=true` | 20000 条目 / 3000 目录条目 / 1500 ms | 只监听顶层与一级子目录，二级以下不监听（明示，不静默） |

**两个不同的预算各被真实触发一次**：扫描侧撞的是**总条目**预算，监听预扫描侧撞的是**单目录条目**预算——
夹具里 `src/` 有 303 个子目录、而 `docs/`/`data/` 各放 10000 个文件，正好把这两条闸门分别打中。

**扩容触发条件**（到这些条件才需要动手，不是现在就该改）：

1. 需要模块图**覆盖全部源码**且源码文件数 **> 20000**：先做分区/分片索引与跨片边聚合，
   或按实际硬件与目标盘重新标定遍历预算。
2. 需要"整棵文件树的精确规模"且条目数 **> 20000**：需要增量式目录索引，或后台可取消的分片扫描
   （当前是**请求内同步有界扫描**，超预算即截断）。
3. 需要监听完整递归且条目数 **> 20000**：需要先建持久化索引再挂监听，否则只能「仅顶层」。
4. 单文件极大（本卡实测 17.4 MB / 20 万行日志）且频繁分页读：分页目前**先整份读回**再算内容哈希与总长，
   第 1 页 151 ms ≈ 整份读回 86 ms；单文件再上一个量级就需要流式哈希。

## 5. 独立放大：任务量 / 事件量 / 关系量

| 维度 | 档位 | 实测 |
| --- | --- | --- |
| 任务量 | 500 张卡 | 施工图解析 89 ms；定义事件导入 2716 ms；上下文包 159 ms |
| 任务量 | 2000 张卡 | 施工图解析 1060 ms；定义事件导入 19968 ms；上下文包 2264 ms（20 个任务进包、3 项进 omitted、13546 字符） |
| 关系量 | 3000 个叶子（每叶子 2 条跨模块 import） | 解析 718 ms；**6000 条 import 聚合成 6 条模块边**（权重合计 6000，7 个模块） |
| 事件量 | 2000 条 | 落盘 5259 ms（约 380/s）；读回 17.5 ms；重放 6.1 ms |
| 事件量 | 20000 条（8.4 MB） | 落盘 54041 ms（约 370/s）；读回 62.7 ms；重放 6.9 ms |

读法：**边聚合真实生效**——6000 条 import 变成 6 条模块边，权重代表依赖强度（§4.3 第 3 招）。
**写入是每条 fsync 的同步路径**（约 370–380/s），是事件量放大的主要成本；重放本身廉价（2 万条 6.9 ms）。
任务量放大里"定义事件导入"同样是逐条 fsync 写入（2000 张卡 20.0 s），是当前最贵的一项。

## 6. 故障与边界场景

- **变更风暴**（1 千档，后台监听 + 3000 次快速写入）：监听就绪后 3000 次写入用 1409 ms（约 2130 次/秒）；
  **等队列静默 4026 ms 后取数**：`changes 3000 = 落盘 3000 + 丢弃 0`，
  且 `changes.jsonl` 的实际行数 3000 = `written`（**第三方口径**对账，不与计数器同源）。
- **超限省略量（洪峰）**：把监听队列上限收紧到 200 后重跑同一规模的写入（3000 次 / 2226 ms），
  等静默 4012 ms 后取数：**真实丢弃 2698 条**，`落盘 1487 + 丢弃 2698 = changes 4185`，
  且 `changes.jsonl` 实际行数 1487 = `written`——洪峰丢弃被计数、落盘不虚报。
- **超限省略量（预扫描）**：10 万条目档转「仅顶层」，`mode=top`、`truncated=true`、
  原因"单目录条目 10000 ≥ 上限 3000"。
- **后台可取消**：关监听 32 ms 内生效，列表不再含该项目；关掉之后新写文件**不再进流水**（真停）。
- **超长日志**（20 万行 / 17.4 MB）：分页取回返回总长（200001 行）、已取范围（第 1–80 行）、
  `status=truncated` 且带续读游标，续读从下一行接着取；**第 1 页只给模型 3989 字符 vs 全文 10,688,890 字符**——
  省的是模型输入量（约 1/2680），不是磁盘 IO（第 1 页 151 ms ≈ 整份读回 86 ms，见 §4 第 4 条）。
- **局部服务故障**：写入服务不可用时写被拒（`SERVICE_UNAVAILABLE`，不自己写文件），
  读退化为磁盘上最后一份快照并标 `stale=true`（旧数据可看，但不冒充当前事实）。

## 7. 备份与恢复怎么用

事实与口径见 DESIGN.md §8.5。**可丢的是缓存与视图；不能丢的是意图、有效决定、任务/执行历史、
检查点、验收和证据。**

### 7.1 备份

- 入口：`createProjectBackup(projectId, { dataDir, destRoot?, backupId?, now? })`
  （`src/server/work/backup.ts`）；备份落点默认在塔台数据目录的 `backups/<project_id>/<backup_id>/`，
  也可由调用方指定（§8.5「用户选择私有备份位置与保留策略」）。**不写回被备份项目一个字节。**
- 备份清单（`backup-manifest.json`）记四件事：**事实源版本**（事件 schema 版本 + 每源自己的版本号，
  如事件源记截止序号、基线流水记末条基线 id）、**截止提交序号** `cutoff_seq`、
  **图纸历史**（全部基线与它们引用的不可变修订副本）、**证据内容哈希与恢复位置**。
- 一致性怎么保证：
  1. 捕获全程持事件文件锁（与唯一写入服务同一把锁）——期间没有事件能追加进去；
  2. 事件文件有半截尾行（上次写入被打断）时**拒绝备份**；
  3. 证据与图纸修订是**内容寻址且不可变**的，按"截止序号以内事件引用到的闭包"物化进备份；
     `git` blob 形态的修订被物化成不可变副本，备份**不依赖原项目 Git 还能不能取回**。

### 7.2 恢复

- 入口：`restoreBackup(backupDir, destRoot)`，**只往隔离目录写**；返回
  `replaced: false` / `replace_requires_user: true`——**是否替换当前数据由用户决定，本模块不自动替换**。
- 恢复前先核验这份备份是不是"某个提交序号的一致切片"（`verifyBackup`，八条判据）：
  ① 清单可解析 → ② 清单哈希与实物相符 → ③ 事实类文件都在清单里 → ④ 事件可重放且序号一致 →
  ⑤ 证据引用闭合且哈希相符 → ⑥ 图纸历史闭合（基线 ↔ 修订恢复位置）→ ⑦ 缓存可由事件重建 →
  ⑧ 捕获时无未解决警告。
- 恢复后在隔离目录逐项复核：**原文可定位**（基线引用的设计/施工修订按恢复位置取回、哈希相符）、
  **证据哈希相符**、**事件可重放**（同一个截止序号）、**缓存可重建**（由事件重建快照，事实不依赖缓存）。
- 恢复旧备份前先看清落后多少：`compareBackupToLive` 报出"当前项目领先备份 N 个提交 / 图纸源是否已变"，
  并明说**替换与否由用户决定**。

### 7.3 哪些方式**不**算通过（反证，必须判不合格）

| 反证 | 结果 |
| --- | --- |
| 跨时刻拼接：事件取自更晚的时间点，其余事实源仍是旧时刻（哈希可对得上） | 不合格（`CUTOFF_MISMATCH` 等） |
| 裸目录副本：直接复制目录、没有备份清单 | 不合格（`MANIFEST_INVALID`） |
| 缺证据：删掉被事件引用的证据正文 | 不合格（`EVIDENCE_MISSING`） |
| 损坏：证据正文被改一个字节 | 不合格（`MANIFEST_HASH_MISMATCH`） |
| 旧基线缺历史：删掉基线引用的不可变修订副本 | 不合格（`BASELINE_REVISION_MISSING`） |

### 7.4 边界

- 备份口径是**项目的 `.工作台/` 私有事实**；附件/二进制大对象、代码仓库本体不在其中（代码进 Git）。
- `chat/`、`logs/` 归归档类：**按策略一并备份但如实标注**"没有 v2 事件提交边界"——它们只有捕获时刻的内容哈希。
- 备份清单里每份文件都有哈希，**清单大小随证据条数增长**（本卡夹具下几十份量级；证据上千条时需评估）。
- 本卡**不演练替换真实数据**；替换是用户在核验通过后的决定。

## 9. 未测范围（如实）

- 真机桌面壳与真浏览器交互未测：上表的 p50/p95 是 **HTTP 端点耗时**，不是浏览器渲染耗时。
- 多用户 / 多人同时写同一项目未测（当前是单写入服务 + 文件锁的单机口径）。
- 跨语言深度：tree-sitter 只覆盖 Python 与 JS/TS；Go/Rust/Java 等未参与规模档。
- 10 万档的**全量**模块图（越过遍历预算后的分区/分片索引）未实现、未测。
- 真实磁盘满 / 只读盘 / 杀进程中断备份等异常路径未测。
- 备份/恢复**替换真实数据**的流程未演练。
- 100 万文件档未测（超出建议档位）。
- 缓存/视图之外的大对象（附件、二进制）未纳入备份口径。

## 10. 口径声明

- 上表档位是**测试档位，不是当前支持承诺**。
- **超大型支持不能由 10 万文件数量单独推出**：本卡实测到的正是"10 万文件档只覆盖到预算上限"，
  而中大型支持还需要再验证跨语言、多人工作目录下的多 Agent 冲突、长周期需求变化与恢复。
  规模上限要由分区、索引与依赖分析的实测共同确定，**不用文件数单独代表业务复杂度**。
