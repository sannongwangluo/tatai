# 正向项目推进闭环契约

来源：2026-10-02 用户要求按五项标准详细检查并安排 Kimi Flash 补足，随后明确逆向落稿暂缓。需求 `req-2026-10-02-forward-loop`，批次 `change-20261002-forward-loop`。本文细化 DESIGN §2.6/§2.7/§2.9、§3.9/§3.14、§5.4—§5.8、§6.7；不另建事实源。

## 分工和边界

Agent 提交事实与证据；塔台负责可靠收录、版本/认领/证据校验、状态派生、页面更新和下一动作。用户验收仍由人操作，新增 Agent 工具不暴露人工 Gate、人工验收或接受风险操作。当前本机单用户 HTTP 是本机信任域，角色字段不是强身份认证；不把这轮扩成对同权限本机进程的安全隔离。逆向落稿保持既有实现，不增加功能、不作为正向流程前置。

## F1 正向基线与可发现入口

已有 DESIGN/PLAN 可以直接读取当前修订、审定并激活成套基线，不经模型生成、不要求制造差异。复用 documents 的保留/校验/激活函数，通过唯一服务宿主供 MCP 和页面调用；不得在 stdio 进程另建写者。新增 `manage_baseline` 的 read/preserve/activate 操作：read 只读；激活须有当前两份源的 expected 哈希、审定者、审定依据；MCP 限授权设计/协调角色，审定类型固定 delegated_technical_review，不得声称 user_confirmation。用户页面可显式操作现有成套文档。缺失、结构冲突、读取后源变化明确拒绝。激活只影响配套基线，不写 Gate，不自动领取任务。缺基线的 project_entry 给真实工具名称和读取/操作顺序。文档源路径沿现有注册配置，说明默认路径和配置入口，不复制第二份当前稿。

## F2 所有相关页面自动同步

施工、验收、设计/待议、项目信息、顶部阶段/当前卡/版本、待决事项、Gate、技术图状态色和数据流目标证据层必须自动重新取数；已有主图和实况机制保留有效语义。复用共同小型 React 刷新机制，默认可见页面 5 秒对账，回前台立即补拉，同一加载器不得并发堆积；即使只变文档、Gate、证据而账本序号不变，也能最终追平。不要只监听 task_last_seq 就宣称覆盖所有来源。后台刷新保留最后成功数据及输入/选择/滚动，失败显示陈旧/原因/最近成功时间，恢复后自行清除。换项目、卸载和晚到旧请求不能串数据或回退。普通刷新不弹窗、不改布局、不自动触发逆向落稿或模型。验收文字、待议草稿、Gate说明按项目隔离保存（至少当前会话切换不丢）。图状态失败不能清空为健康。显示真实任务 updated_at、成果提交者/时间；无回执只能说未观测，不猜失败或停止。

建议公共接口（由 V09-26 提供，V09-28 消费）：
```ts
export function useProjectRefresh(projectId: string, options?: { intervalMs?: number }): number;
```
返回单调刷新 token；挂载、可见轮询、重回前台、在线恢复触发。调用页负责取消本轮在途回包和保留最后成功值。若改成包含状态的返回类型，必须兼容这个数字接口或同步消费者，不能并行各造一套。

## F3 Agent 完整上报与回执

保留 v1 行为。扩展 `report_task_status` 的 v2 输入使 doing/blocked/恢复 ready 能带 expected_revision、claim_token、owner、request_id 和原因经唯一写服务提交；done 必须指向 submit_task_result，不能绕证据把完成写成已验收。服务侧验证当前认领/持有者、版本、状态与恢复依据；旧工具缺参返回升级指南，不能默默回退到 tasks.json。保留领取、结果提交、reopen 等既有入口。

新增 `report_execution`（启动回执/心跳/检查点/停止/失败等既有执行事件的受控适配）与 `record_work_evidence`（证据保存/读取、成果登记、自检、独审、缺陷、修复、复测的受控适配）。复用既有 executionReceipts、audit、evidence 校验，闭键、按操作严格校验，新增 Agent 工具不接受 user 身份或人工验收/风险豁免操作。事件经 ctx.work 转接，证据正文由服务宿主保存不可变内容；不得泄漏服务令牌。返回真实 await 后的回执；本地计划占位不能出接口。证据/审计记录有明确版本、对象和来源，不自动把执行者的验证声明转换成独立审计。

相同结果请求在响应丢失后重试，应得到原提交回执 duplicate=true；同幂等身份却内容变化明确拒绝。重试不能因任务已经提交而只给 VERSION_CONFLICT，不能绕新请求的当前版本/租约/依赖校验。新工具同样支持稳定 request_id；测试必须经工具入口而不是只调库。

执行现场用现有 livenessOf/readExecution 接入 project_entry.current_runs：最后回执/检查点、未知/长时间无观测/停止未确认/已结束；无事件为未知，无心跳不等于停机。不新增自动重派和进程启动器。

唯一写服务的恢复也遵守同一原则：探活超时但描述符所指进程仍存在时，只能报告不可达/所有权待核实，不能据此不断拉起第二个写宿主。现有启动/接管机制要核实存活与所有权；失去描述符所有权的后台发现不能继续冒充当前宿主。这是既有唯一写者边界的修复，依据本轮实际安装服务十五秒健康读超时及同 home 多个 daemon 现场（`runtime-observation.md`），不新增调度平台。

## F4 证据有效性和来源变化

task.result_submitted 只是交付记录，存在的路径可作为材料，不自动判验证通过。可用于“已验证”的检查必须绑定当前可核对来源；源变化按声明覆盖范围使旧检查失效，不能以账本中上次自报的 code revision 反过来当当前代码版本。新证据入口可登记有限、可取回、项目内的源文件清单及内容哈希；现读变化或缺失给 invalidated/unverified。未知范围明确需复核，不编造当前哈希、不扫描私密或忽略目录、不无限全盘散列。历史证据原样保留，不删除或重写原始事件；无法证明当前有效的旧自报不冒充新鲜验证。设计/施工分段失效已有实现复用。该项先独立构造源码改动反例，再确定最小改法。

成果只提交一次时，验收页应能看到 task.result_submitted 已有的交付/验证/未测/已知问题信息，不能要求 Agent 为了展示再人工重复登记 audit.submission；用只读适配保留正式审计与执行自报的区别。

## F5 完整旅程验收

隔离 home/项目/动态端口、真实写服务及 MCP 工具调用：现有两份图纸→技术审定激活→需求/定义登记→领取→开工→阻塞→恢复→检查点→提交/同次重试→自检与独审→打回→新 attempt 修复/复测→用户界面验收→重启/新客户端读取接续。所有人工动作只在测试夹具由测试用户模拟，真实 Gate 不写。断言账本、读口和真实浏览器页面同源变化，错误/旧响应/断线恢复/切项目/草稿保留有反例。源码检查、工具验证、浏览器与安装产物证据分别标注，不互相冒充。
